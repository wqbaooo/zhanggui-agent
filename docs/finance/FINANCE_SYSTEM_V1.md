# 掌柜 Agent 单店财务系统 V1 实施契约

> 状态：V1 已实施，持续校准的 source of truth
> 适用门店：`xinyu-hengtai-dakou`
> 核算起点：2026-07-01
> 目标：让营业额、利润、资金、库存、投资和债务可以由同一套底账重算、追溯和预警。

## 1. 产品边界

本系统同时提供两层能力：

1. **经营管理会计**：日/周/月利润、保本、成本、单品、渠道、现金预测和经营预警。
2. **规范财务底账**：按权责发生制区分收入、费用、资产、负债、老板投入与资金到账。

非目标：V1 不自动报税，不声称替代持证会计生成法定报表。但所有数据必须可导出给外部会计复核。

## 2. 不可破坏的核算原则

- **收入与到账分离**：销售发生时确认营业收入；前老板代收、平台待结算只改变应收和资金位置。
- **会计收入与老板到手口径并行**：老板端以“实际到手营业额”作为每日第一经营指标；它记录平台确认给门店的净得额与现金，但不替代会计营业收入，也不等于利润。
- **业务事实与会计分录分离**：截图识别结果不能直接成为利润；确认后的业务事实才能触发过账。
- **库存采购与销售成本分离**：采购先增加存货，只有领用/销售/报损才转为当期成本。
- **老板资金与店铺收入分离**：老板投入、借款不是营业收入；老板取款不是经营费用。
- **实际利润与老板机会成本分离**：当前实际员工为 1 人，月薪 5,200 元，加班 16 元/小时；老板不计入员工工资，机会成本未确认时为 `null`。
- **未知不等于零**：任一必需项缺失时，对应指标返回 `null + blocking_reasons`，禁止用 0 补齐。
- **分录平衡**：每张记账凭证的借方合计必须等于贷方合计，不平衡不得过账。
- **不可静默改账**：已过账记录通过冲销和调整分录修改，不直接覆盖。

## 3. 后端分层

```text
Capture Layer
  原图/OCR/平台报表/Excel/手工录入
        ↓
Fact Layer
  待确认经营事实 + 去重 + 证据关联
        ↓
Posting Layer
  会计科目 + 凭证 + 借贷分录 + 会计期间
        ↓
Subledgers
  销售 / 资金 / 应收应付 / 库存 / 工资 / 资产债务
        ↓
Metric Engine
  利润 / 成本 / 保本 / 单品 / 渠道 / 现金预测
        ↓
Read Models
  日报 / 周报 / 月报 / 前端 / Agent / Excel
```

存储选择：V1 使用 SQLite，开启 foreign keys 和 WAL。数据库是唯一账务 source of truth；JSON 在迁移完成后只作历史快照和导入源。数据库结构通过 `schema_migrations` 升级，业务过账规则通过版本化 `posting_templates` 管理，禁止把关键借贷规则散落在路由或页面中。

## 6. 指标引擎合同

指标不允许在 React 页面临时推导。后端指标注册表必须声明：`metric_code`、`version`、`formula`、`basis`、`required_inputs`、`blocking_rules`、`period`、`calculated_at`、`source_entry_ids`。

| 指标 | 公式 | 阻断条件 |
|---|---|---|
| 实际到手营业额 | 各渠道门店净得额 + 现金销售 | 渠道净得额无截图且无可信来源 |
| 已到店铺可控账户 | 店铺现金 + 店铺专用银行/钱包可用余额 | 账户归属或资金位置未知 |
| 营业收入 | 已确认销售收入 - 销售退回与调整 | 收入主证据未确认 |
| 客单价 | 营业收入 / 有效订单数 | 订单口径未知 |
| 食材实际耗用 | 期初库存 + 采购 - 期末库存 - 非销售调整 | 期初/期末盘点缺失 |
| 营业毛利 | 营业收入 - 食材 - 包装 | 销售成本未确认 |
| 贡献毛利 | 营业收入 - 全部变动成本 | 平台/活动/包装成本不完整 |
| 经营净利润 | 贡献毛利 - 固定经营费用 | 任一必需成本未确认 |
| Prime Cost | 食材 + 包装 + 员工人工 | 库存耗用或工资未确认 |
| 月保本营业额 | 月固定成本 / 贡献毛利率 | 贡献毛利率不可用 |
| 月目标营业额 | (月固定成本 + 目标利润) / 贡献毛利率 | 目标利润未设置 |
| 单品贡献毛利 | 实际售价 - BOM - 包装 - 渠道变动费 | BOM/渠道成本缺失 |
| 现金可支撑天数 | 可用资金 / 近 N 日平均必要现金支出 | 未实点资金或支出样本不足 |

### 比率展示规则

- 分母为 0 时返回 `null`，不返回 0%。
- 比率保留至少 4 位小数存储，前端只负责格式化。
- 日、周、月均由日期范围聚合，不以“最近 N 条”代替日期范围。
- 保本分析属静态模型，同时展示乐观/基准/保守三档敏感性，不将单一假设冒充确定结论。

## 7. 专业报表体系与经营分析

### 利润表

`营业收入 -> 销售成本 -> 营业毛利 -> 变动销售费用 -> 贡献毛利 -> 固定经营费用 -> 经营净利润`。

### 资产负债表

资产包含现金、银行、平台待结算、前老板应收、存货、押金和设备；负债包含供应商、工资、借款与其他应付；差额归属老板权益。

### 现金流量表

- 经营活动：销售到账、采购付款、工资、房租、水电和其他经营支出。
- 投资活动：转让费、押金、设备、装修。
- 筹资活动：老板投入/取款、借款/还本。

## 8. 每日打烊闭环

`daily_close_session` 按营业日管理。用户打开产品时，如前一营业日未结账，Agent 主动询问：

1. 导入客如云单日营业简报；订单金额不是实际到手，只有营业收入公式与支付方式合计同时通过时，才确认当日实际到手营业额。
2. 每笔门店净得额当前位于平台钱包、绑定银行卡、前老板代收还是店铺可控账户。
3. 当日银行卡、微信、支付宝和现金等多渠道实际资金流出是否已复核。
4. 收银机实点现金、预备金目标和差额。

食材耗用、包装、房租、水电、加班等按事实发生自动进入待确认，不作为每天强制关账字段。缺失成本只阻断利润确认，不阻断老板完成资金盘点。

状态：`open -> awaiting_inputs -> ready_for_review -> closed -> reopened`。只有 `closed` 才生成正式日报；重开必须写入原因和审计日志。

### 财务经营系统界面边界

- **资金流是默认视图**：按“资金来源 -> 当前资金位置 -> 最终用途”展示营业收入、平台钱包、前老板代收、店铺支出、老板往来和借款；每笔直接关联原始凭证。
- **银行卡实际余额不能推算**：累计收款、账面资金轨迹与银行卡实时余额必须分开。没有余额截图或完整银行流水时显示“待银行流水核对”，禁止拿累计到账冒充余额。
- **记账本是一个操作功能**：支持手工记一笔和查看逐笔流水，但不能取代资金预测、对账和利润核算。
- **账单录入**：银行、支付宝、微信和平台 CSV/Excel/PDF 先校验行数与收支合计，再生成待确认记账；同文件同账户按 SHA-256 幂等去重。
- **凭证库**：原文件、图片、识别字段、人工修改、资金流水和会计分录必须双向关联。
- **历史日期**：同时展示“当日发生”和“截至当日资金位置”，禁止使用当前余额污染历史快照。

未来资金公式：

`截至当日可控资金 + 预计到账 - 必须付款 - 安全备用金 = 可自由使用资金`。

若滚动余额首次低于安全备用金，返回 `first_risk_date + shortfall_minor`；未来收付未登记完整时状态只能是 `partial`，不能声称安全。

## 9. 预警规则

V1 必须实现：

- 打烊实点现金 ≠ 账面现金。
- 平台或前老板应收逾期。
- 未来 7/30 天可用现金低于已知必付款。
- 工资、房租、供应商应付将到期但资金不足。
- 经营净利润为正但经营现金流持续为负。
- 采购增加但销量/库存无法解释。
- 实际食材/耗材率超出移动基线，不在无店铺基线时硬写行业阈值。
- 连续未完成打烊、重要账单待确认或日报存在重复数据。

## 10. Agent 架构契约

LLM 只负责问题理解、工具编排和解释。金额和比率只能来自财务查询服务。

```text
用户问题
  -> 意图和时间范围
  -> finance_query_service
  -> 指标完整度和冲突检查
  -> 返回数值 + 公式 + 来源 + 缺口
  -> LLM 翻译成老板可理解的回答
```

回答契约：`answer`、`period`、`metrics`、`formula_trace`、`evidence_ids`、`completeness`、`warnings`、`follow_up_inputs`。任何回答均不允许通过问题关键词硬编固定文案代替查账。

## 11. Excel 边界

- 导入：平台报表、银行流水、历史收支、盘点表。
- 导出：日/周/月利润表、现金流、应收应付、债务、单品成本、平台对账、全部分录。
- Excel 行需带 `record_id`、`source_id`、`status`、`accounting_period`，再导入时幂等去重。
- Excel 不是 source of truth，不保存唯一有效公式。
- 用户每日只在产品完成一次关账；下载工作簿可包含多个专业账簿和报表，但不得要求用户重复填写多个 Sheet。
- 原始截图作为凭证保留，导出的明细账必须带凭证编号、原始来源、证据状态和截图索引。

## 12. 7月1日至10日迁移规则

1. 原始截图和当前 JSON 全部作为 immutable source records 导入。
2. 客如云显示营业额作为会计收入参考与差异控制，不作为老板端第一经营指标；老板端“实际到手营业额”按各渠道净得额和现金求和。
3. 已确认的期间总收入 11,879.78 元、788 单、客单价 15.27 元作为迁移对账锚点。
4. 前老板代收迁移为应收资产；转款回单只用于核销应收。
5. 美团、淘宝闪购等平台余额截图可确认“已入平台钱包”，但不能自动确认“已到本人店铺账户”；抖音在权限未交接期间标记为 `permission_blocked + keruyun_only`。
6. 无法确认的京东覆盖关系、现金实点、食材耗用和完整费用保留为 open gaps。
7. 不迁移旧模拟利润、回本期、默认成本率或模拟现金余额为真实数据。
8. 迁移后必须通过：实际到手营业额合计、会计收入合计、平台去重、资金路径、借款本金与用途、借贷平衡、应收核销、缺失指标为 null。

## 13. API 读模型

V1 公开合同：

- `POST /finance/facts/{id}/post`：将已确认事实幂等过账。
- `GET /finance/overview?from=&to=`：营业收入、成本、利润、资金、应收应付、完整度。
- `GET /finance/statements/profit-and-loss`、`balance-sheet`、`cash-flow`。
- `GET /finance/metrics/{metric_code}?from=&to=&dimension=`。
- `GET /finance/reconciliation/platforms`、`cash`、`receivables`。
- `GET/POST/PATCH /finance/bookkeeping`：查看和补充记账记录；老板在录入页面点击“确认记入”后，一次性写入资金账、凭证关系和安全的会计分录，不再要求第二次通用复核。
- `POST /finance/imports`：导入银行、支付宝、微信或平台账单，保留原件并生成待确认逐笔流水。
- `POST /finance/report-imports/preview`：识别客如云营业简报或平台官方财务报表，只预览、不改账。
- `POST /finance/report-imports/confirm`：校验后归档原件；客如云确认单日销售，平台钱包入账/提现只生成待核对资金记录。
- `GET /finance/reconciliation/queue`、`POST /finance/reconciliation/{id}/match`：逐笔匹配平台净得额、资金流水和银行到账。
- `GET /finance/daily-snapshot?date=`：返回当日发生、截至当日资金位置、凭证和关账状态。
- `GET /finance/cash-forecast?as_of=`、`POST /finance/cash-plan`：未来 7/14/30 天资金预测和计划收付。
- `POST /finance/daily-close`、`POST /finance/daily-close/{date}/reopen`。
- `GET /finance/alerts`。
- `GET /finance/export.xlsx?report=&from=&to=`。
- `POST /finance/query`：Agent 使用的结构化查账接口。

## 14. 验收门槛

- 同一业务事实重复过账不会重复增加收入。
- 每张凭证借贷平衡，全部子账可追溯到原始证据。
- 利润表、资产负债表和现金流量表可以按日期重算。
- 没有完整成本时净利、毛利率和保本营业额为 `null`。
- 前老板转款和平台结算不改变已确认营业收入。
- 前端与 Agent 对同一时间范围和口径返回相同数值。
- 日报、Excel 和 Agent 答案都包含口径、完整度和证据链。
