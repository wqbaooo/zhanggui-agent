# 大口章鱼烧｜财务事实与平台对账契约

> 本文是财务录入、截图识别、凭证留存、过账、对账、报表和 Agent 回答的共同口径。没有原始来源的金额不得自动生成；识别不确定时必须保留为空或标记待确认。

## 1. 一项钱的四层事实

1. **证据**：原始图片、PDF、Excel、银行流水或人工说明。文件以 SHA-256 去重并原样保存。
2. **业务事实**：图片真正证明的日期、金额、渠道、资金位置、用途与置信度。
3. **资金流水**：实际发生的收款、付款或账户间移动。
4. **会计分录**：只有经老板确认且满足会计条件的事实才产生。没有完整成本或库存资料时利润为 `null`。

证据不是分录；平台到账不是新销售；采购付款不是当期食材成本。

## 3. 事实类型、必填字段与状态

| 事实类型 | 必填确认字段 | 凭证 | 结果 |
|---|---|---|---|
| 实际到手营业额 | 营业日、渠道、净得额、资金位置 | 平台余额/结算截图，或人工说明 | 每店/营业日/渠道一条聚合事实；可更新，不重复累加 |
| 平台结算到账 | 到账日、到账金额、实际收款账户、来源平台 | 银行到账截图 | 进入资金流水和对账队列；未匹配前不增加收入 |
| 前老板转回 | 到账日、金额、收款账户、前老板 | 银行到账截图 | 核销前老板应收；不增加收入 |
| 店铺费用 | 付款日、金额、付款账户、费用性质、对方 | 付款凭证/单据 | 进入待确认账；确认后才影响费用 |
| 进货 | 付款/到货日、金额、账户、供应商、货品 | 进货单/付款凭证 | 先进入库存；盘点/领用后才进入成本 |
| 个人消费 | 日期、金额、个人账户、用途 | 凭证可选但推荐 | 保留资金去向；不进入店铺利润 |
| 借款/老板资金 | 日期、金额、对方、用途 | 借据/转账凭证 | 负债或权益；不算营业收入 |

状态顺序：`原图已保存 -> Agent 识别并生成可编辑表单 -> 老板确认记入 -> 已记录/待到账/待对账`。老板在录入页点击“确认记入”就是本次人工核对，不再生成第二个含糊的“待复核”步骤。只有金额、日期、账户、用途发生冲突或缺失时，记录才停在“需要补信息”。

前端只展示业务状态：`需要补信息 / 已到平台钱包 / 前老板代收待转 / 待到账 / 待对账 / 已完成 / 已作废`。模型置信度、底层草稿状态和会计过账状态保留在审计层，不作为老板日常台账的重复操作。

店铺日常分类固定为：`营业收入 / 店铺进货 / 固定开支 / 日常经营 / 接店与资金 / 老板往来`。个人消费、老板取用、老板垫付和正式工资必须分别表达，不能只因使用同一张银行卡就混成店铺费用。

### 官方报表证据优先级

1. 客如云单日营业简报：用于确认当日经营净收款；必须同时满足单一营业日、来源公式差额为 0、支付方式合计差额为 0。
2. 美团/淘宝闪购/京东/抖音官方财务报表：用于拆分平台钱包入账、扣费、提现及待结算，不把提现识别为新收入。
3. 银行、支付宝、微信流水和到账截图：用于证明钱实际到哪个账户，以及核销平台待结算或前老板应收。
4. 进货单、付款单、工资、房租、水电和其他支出凭证：用于库存、费用、应付和资金流出。
5. 无法识别来源、日期、金额或关键字段的文件：只入凭证库并标记待确认，不自动写账。

## 4. 固定公式与禁止混算

```text
实际到手营业额 = Σ(营业日 × 渠道 的已确认门店净得额) + 已确认现金销售
```

客如云单日营业简报的固定校验：

```text
实际到手营业额
= 订单金额 - 商户优惠 - 订单配送支出 - 服务费 + 带符号补贴
```

```text
实际到手营业额 = Σ支付方式收款金额
```

两条等式任一不平，整份日报停止自动确认。平台补贴使用源文件正负号，不擅自取绝对值。

```text
店铺可控资金 = 截至查询日，店铺控制的现金 + 店铺专用银行卡/钱包余额
```

```text
经营资金差额 = 实际到手营业额 - 店铺多渠道实际流出
```

上式只用于资金观察，**不是利润**。

```text
经营净利润 = 已确认营业收入 - 食材实际耗用 - 包装实际耗用
           - 平台佣金/配送/推广 - 工资 - 房租 - 水电 - 其他经营费用
```

若营业收入已经采用平台扣费后的门店净得额，同一笔佣金、配送费、推广费不得再次扣减；只有能从“平台原始售额”开始完整还原的平台利润分析，才单列这些费用。

任一必要输入缺失时，经营净利润、毛利率、保本营业额为 `null / 不可确认`，不得补 0 或估造数值。

```text
可自由使用资金 = 截至当日可控资金 + 预计到账 - 必须付款 - 安全备用金
```

未来工资、房租、进货、还款或预计到账没有登记完整时，资金预测状态为 `partial`，不得显示“安全”。

## 5. 事实冲突处理

- 同一图片：按 SHA-256 去重，不产生第二张凭证。
- 同一营业日、同一渠道：更新同一条渠道净得额聚合事实，保留凭证链；不叠加成两次收入。
- 平台净得额与银行到账：金额、日期、平台、账户用于对账；匹配后仅移动 `平台待结算/前老板应收 -> 银行`。
- 客如云参考额与渠道净得额不同：保留差异和来源，不自动强行调平。
- 抖音未交接、截图模糊、日期不明：状态为待确认/权限受限；不进入“已确认实际到手”。
- 已入账错误：冲销/调整，不静默覆盖历史。

## 6. 每晚日清顺序

1. 导入客如云当日营业简报，核对营业日、公式和支付方式合计，确认当日实际到手营业额。
2. 导入当天能取得的美团、淘宝闪购、京东、抖音钱包/对账报表；只记录钱包入账、扣费、提现和资金位置。
3. 导入工商银行、支付宝、微信等账户流水或到账截图；与平台钱包、前老板代收逐笔匹配。
4. 录入当天店铺付款、进货、个人消费、老板投入/取用、借款/还款；必须选择实际经过的账户并关联凭证。
5. 复核现金实点、店铺多渠道流出和未匹配资金，完成资金日清。
6. 库存领用/盘点、员工工时、房租水电等成本资料齐全后计算毛利和经营净利润；资料不全时只显示缺口，不显示假利润。

月清是在上述日清基础上完成平台结算核销、银行余额核对、库存盘点、工资计提、固定费用摊销、借款与接店成本复核，并锁定月报。
