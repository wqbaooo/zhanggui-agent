# 餐饮开店 Co-pilot 产品迭代总计划

## 产品目标

把当前产品从「餐饮 SaaS 工作台」迭代为「餐饮创业虚拟合伙人」：

- 从开店前切入：想法、选址、加盟合同、财务测算、装修证照、开业计划
- 开业后自然接管：经营账本、营销、会员、复盘、连锁拓展
- 所有建议必须基于统一项目账本、案例依据和可执行任务

核心产品共识：

> 店外长进去，店内长出来。先占住开店前无人服务的 60% 关键链路，再用真实经营数据接管运营复盘。

补充判断：

> 右半段不是次要能力。对已经选好址、准备接店或已经开业的用户，运营接管、复购增长和复盘优化是价值兑现区。左半段负责降低开店错误，右半段负责让店活下来并持续赚钱。

## 战略判断

### 应采纳

- 数据孤岛是 P0：所有页面必须读同一个项目账本。
- 筹备期和运营期必须打通：财务测算、选址假设、开业预算要在运营期被验证。
- Mock 与真实数据不能混用：没有数据时显示缺失状态，不用样例数字伪装经营结果。
- AI 建议必须有来源和动作：建议要带用户数据、案例、方法论或假设，并能生成任务/打开工具。
- 22 个模块不应全部暴露为主界面：模块是 Agent 工具，不是用户的第一认知。

### 需要降级落地

- 美团/POS API 接入不能假设立即可用。先支持手工录入、导表、截图/OCR，再做 API/RPA。
- “虚拟合伙人”是定位，不是第一版能力。第一阶段必须先做到可信账本和任务闭环。
- 运营、复购、连锁拓展必须覆盖。只是进入方式不同：从筹备假设和真实经营账本自然长过去，而不是复制一个普通餐饮 SaaS。

## 对标不是照抄

参考对象的价值：

- Toast：证明餐饮 OS 可以从 POS/支付切入，扩展到订单、会员、库存、金融。
- 有赞/客如云：证明国内餐饮经营系统会往 AI 智能体和托管运营走。
- Zavo：证明“AI operating system for restaurants”是成立的新叙事。
- Harvey/Hebbia：证明垂直 Agent 的护城河来自专业知识、证据链和可执行工作流。

我们的超越路径：

1. 不从 POS/收银开始，而从开店前的决策和筹备切入。
2. 不只服务已开业老板，也服务第一次加盟/转租/开店的人。
3. 不只做运营看板，而把选址、合同、财务、开业 SOP、日账、复购、复盘连成闭环。
4. AI 不只是解释数据，而是把建议变成任务、工具调用、复盘和下一轮实验。
5. 长期形态不是餐饮 SaaS，而是餐饮创业 Co-pilot / 虚拟合伙人。

## 产品边界修正：项目评估域与门店运营域分开

上一版把“想法验证 → 开业 → 运营”画成一条连续生命周期，方向没错，但主界面逻辑会割裂：

- 前期调研的单位是“项目/机会”：用户还没确定品牌、铺位和投资模型。
- 运营操作系统的单位是“门店”：品牌、铺位、账号、菜单、人员和数据源已经确定。
- AI Agent 的单位是“任务/证据链”：它跨两个域工作，但不能把两个域混成一个页面。

新的产品结构按三类产品参考：

| 产品域 | 参考对象 | 本产品职责 |
| --- | --- | --- |
| 加盟/开店决策 | 加盟平台、选址工具、合同审查工具 | 评估项目是否值得做，拆合同、算投入、看案例、做 Go/No-Go |
| 门店运营 OS | Toast、客如云、有赞、收银/POS、外卖商家后台 | 以单店为对象接管日账、订单、外卖、库存、人效、评价、复购和复盘 |
| AI Agent | Manus、Harvey、Hebbia、垂直 Copilot | 把数据缺口变成任务，把建议变成执行，把复盘反哺知识库 |

当前新余恒太城项目已经确定品牌和铺位，所以默认进入“门店运营 OS”。前期调研保留为独立工作域，不再压在首页第一屏主线里。

## 多层次用户与入口

产品不能只按“第一次开店小白”设计。至少要覆盖三层用户：

| 用户层级 | 核心需求 | 产品入口 |
| --- | --- | --- |
| 新手创业者 | 不踩坑、算清账、知道今天做什么 | 项目评估域 + 单店运营引导 |
| 单店老板 | 把这家店跑起来，少亏钱，多复购 | 门店运营 OS |
| 超级加盟商/区域代理 | 信息差、品牌判断、多店复制、商业顾问 | 加盟工作台 |

因此首页入口调整为：

1. `加盟工作台`：信息差、品牌机会、商圈机会、案例雷达、我的店铺/机会。
2. `门店运营 OS`：进入具体门店后，围绕日账、外卖、库存、人效、评价、复购和复盘。
3. `AI 任务层`：把缺失数据和建议写入任务，跨项目评估和门店运营推进。

超级加盟商视角的关键不是“更大看板”，而是商业顾问能力：

- 识别品牌招商话术和真实单店模型之间的差异。
- 从加盟商、超级加盟商、投资人、房东、平台和失败案例中积累信息差。
- 多店横向比较：同品牌不同商圈、同商圈不同品类、同品类不同经营模型。
- 把一个单店能否复制，拆成店长 SOP、人效模型、供应链稳定性、选址条件和老板脱身能力。

真实接入原则：

- 不把“待接入”写成“已接入”。
- 第一阶段先做手工录入、CSV/Excel、截图/OCR、导出文件解析。
- 美团、饿了么、抖音、小红书、私域和 POS 接入必须区分：官方 API、商家后台导出、RPA、人工录入。
- 没有授权和真实数据前，只展示接入路径、采集清单和任务，不展示虚构订单、ROI 或评价。

## 当前 P0

| 问题 | 影响 | 验收标准 |
| --- | --- | --- |
| 工作台硬编码经营数字 | 用户不信账 | 工作台所有 KPI 来自 `/api/projects/{id}/cockpit` |
| 数据分析/营销/人员等模块仍有 demo | 页面互相打架 | 未接真实数据的模块显示“待接入/未录入”，不显示精确假数据 |
| 筹备期 baseline 没进入运营期 | 全生命周期不成立 | 财务测算保存后，工作台展示预期 vs 实际 |
| AI 下一步行动不可执行 | 不是 Agent | 行动项能打开目标工具，后续升级为任务写入 |

## 6 个月路线

### 第 1 阶段：统一账本与生命周期驾驶舱

目标：

- 后端增加 `cockpit` 统一入口
- 前端首页变成生命周期驾驶舱
- 工作台不再使用 mock 经营数据
- 数据缺失状态专业、明确、可行动

已开始：

- `ProjectMemory.cockpit_summary()`
- `GET /api/projects/{project_id}/cockpit`
- 前端 `getProjectCockpit()`
- 工作台读取 cockpit 数据

### 第 1.5 阶段：运营增长右半段增强

目标：

- 工作台第一屏同时展示开店前链路和开业后链路
- 运营接管、复购增长、连锁拓展用 30/60/90 天作战图呈现
- 右半段不再藏在菜单里，而是成为经营目标区
- 已选址用户进入产品时，默认判断不应停留在“要不要找铺”，而要推进接店、试营业、日账、外卖、复购和品类备选

验收：

- 用户一眼能看到“开业后怎么活”：日账、外卖、复购、库存、人效、复盘
- 没有真实数据时显示待接入状态，不显示虚假增长数字
- 竞品、营销、人员、库存、会员、菜单等右半段模块未接真实数据时，展示采集清单和下一步动作，而不是编造月销、评分、ROI 或复购率

已完成：

- 首页增加 30/60/90 天运营增长区：运营接管、复购增长、连锁拓展
- 数据分析、营销 ROI、人员、库存、会员、菜单优化改为统一账本或可信空状态
- 竞品调研、开业营销、设备交接、风险登记改为新余恒太城接店语境

### 第 2 阶段：筹备期 baseline 打通运营期

目标：

- 财务测算结果保存为 baseline
- 选址假设保存为 site baseline
- 开业营销预算保存为 launch baseline
- 运营期展示预期 vs 实际

验收：

- 任意 baseline 保存后，刷新工作台仍可见
- 无 baseline 时显示缺失项，不显示假数据

### 第 3 阶段：Agent 行动闭环

目标：

- 每条建议生成任务
- 任务可关联工具、数据字段、截止日期和复盘结果
- 行动完成后写入项目档案

验收：

- 点击“补齐：连续 7 天经营流水”进入收支记账
- 后续升级为创建 `Task`

### 第 4 阶段：案例与合同护城河

目标：

- 案例库按城市层级、品类、加盟/自营、商场/街边、人工模式检索
- 合同与加盟风险输出来源和条款级检查点
- AI 建议引用案例编号，不堆理论名词

验收：

- 工作台建议可显示“依据：用户流水 + 案例库 + 当前假设”

### 第 5 阶段：数据接入

目标：

- 手工录入
- CSV/Excel 导入
- 收银机截图/OCR
- 美团/外卖导出文件解析
- API/RPA 作为后续增强

验收：

- 一个店能从无 API 状态跑通真实账本

## UI/UX 原则

- 第一屏是「今天该怎么推进」，不是模块目录。
- 生命周期进度条是主骨架，左侧菜单只是次级工具入口。
- 没有数据时要设计成可信的缺失状态，而不是空白或假数据。
- 卡片半径控制在 8-12px，色彩以白/灰/暖橙/墨蓝为主，语义色只用于风险和状态。
- Agent 行动要可点击，用户能顺着行动进入工具。
